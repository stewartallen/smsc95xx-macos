Every value agrees with the userspace probe reading the same silicon, which is the point of
publishing them: the dext's transport is checked against an independently proven implementation
rather than against expectation.

Two incidental confirmations in the same capture:

  - IOUSBHostFamily itself logs "SMSC95xxDriver selected configuration 1", so the claim that this
    device arrives unconfigured and that our driver is what configures it does not rest solely on
    reading ioreg.
  - The interface node appears as
        +-o IOUSBHostInterface@0  <class IOUSBHostInterface, !registered, !matched, active>
    i.e. created by our SetConfiguration(1, false) but deliberately NOT published for other drivers
    to match, which is exactly what matchInterfaces = false is for.

MII registers live at offsets >= 0x100 (MII_ADDR is 0x114) and stall on an unconfigured device, so a
successful PHY ID read is also proof the configure step worked.

   device in 0x9E00 state -- EEPROM auto-load FAILED
=======================================================================

Reached by luck on a real power cycle; the auto-load failure is intermittent on this unit.

kernel: (…smsc95xx.driver.dext) SMSC95xx: device arrived unconfigured; selected configuration 1
kernel: (…smsc95xx.driver.dext) SMSC95xx: ID_REV 0x9e000002 chip 0x9e00 rev 0x0002
kernel: (…smsc95xx.driver.dext) SMSC95xx: PHY ID 0x0007:0x4165
kernel: (…smsc95xx.driver.dext) SMSC95xx: E2P_CMD auto-load NOT loaded
kernel: (…smsc95xx.driver.dext) SMSC95xx: EEPROM signature mismatch: offset 0 read 0x4a, expected 0xa5
kernel: DK: SMSC95xxDriver::start(IOUSBHostDevice) fail
kernel: DK: IOUserServer::terminate(SMSC95xxDriver) server exit before start() instantiated 1

Both provenance signals disagreed with a good read, the driver refused, Start() failed, and teardown
was clean. No address was invented and no properties were published. Linux's in-tree smsc95xx
configures the resulting bogus 4a:f8:f8:c2:c2:f2 and reports success; this refuses.

Note also that ID_REV still reads 0x9E000002 in this state: it is the chip identity register and is
unrelated to the USB product ID, which is what changes with EEPROM state.

NOT YET EXERCISED ON HARDWARE: v1.2 added an explicit gate on the E2P_CMD LOADED bit, so a failed
auto-load is now refused at that check rather than at the signature. The capture above predates it,
and every power cycle since has auto-loaded successfully. The signature gate is proven; the LOADED
gate is proven only by construction, being structurally identical and four lines long.


=======================================================================
4. FOUR REQUIREMENTS FOR A DEXT TO LOAD
=======================================================================

None of these produces a diagnostic that points at itself, which is the reason for writing them down.

1. arm64e, NOT arm64.
   A plain arm64 dext builds, links, signs, stages and activates without complaint, then:
       kernelmanagerd: Error … "DextLaunch(…)": NSPOSIXErrorDomain Code=8 "Exec format error"
       kernelmanagerd: job failed to spawn … SandboxProfile => com.apple.dext
   Nothing about the IOKit personality is wrong; the Mach-O will not exec. Apple's own dexts in
   /System/Library/DriverExtensions are arm64e (plus x86_64). DriverKit on Apple Silicon requires
   pointer authentication.

2. The bundle must be named <CFBundleIdentifier>.dext.
   Named SMSC95xxDriver.dext, activation fails with OSSystemExtensionErrorDomain code 4, "Unable to
   find any matched extension with identifier …" -- even though the identifier in Info.plist is
   correct and NSBundle bundleWithPath: reads it back correctly. Isolated by single-variable test;
   Apple's shipped dexts follow the same convention. (The executable inside was renamed at the same
   time, so that half is not independently isolated.)

3. OSBundleUsageDescription is mandatory.
   Error code 9 states it outright for the com.apple.system_extension.driver_extension category.
   Apple's preinstalled dexts do NOT carry this key, because they are never installed through
   OSSystemExtensionRequest -- so their Info.plist is not a usable template.

4. A personality matching IOUSBHostDevice must not require bConfigurationValue or bInterfaceNumber.
   Those are IOUSBHostInterface properties. A device node has neither -- verified against the live
   node's full property list -- so such a dictionary never matches, and nothing reports an error.


=======================================================================
5. RULED OUT -- these are NOT the cause, do not re-investigate
=======================================================================

- Bundle layout. Wrapping the dext in a Contents/ directory changes nothing. Flat is correct:
  Info.plist and the executable at the top level.
- CFBundleExecutable. The dyld shared cache does contain the string "CFBundlePackageType is DEXT and
  bundle declares CFBundleExecutable; use only one", but removing the key changes nothing, and
  Apple's own AppleUserECM dext declares both.
- The family.networking entitlement. Dropped while chasing the wrong cause, then restored; the dext
  attaches with it present, and M4 needs it.
- App bundle location. The installer being outside /Applications is not what causes the SIGKILL; the
  restricted entitlement under an unauthorised signature is. Both were tested from the same directory.


=======================================================================
6. OPERATIONAL NOTE: upgrades can half-apply
=======================================================================

A dext holding a device open does not terminate when replaced. The new version stages,
systemextensionsctl reports it "activated enabled", and the kernel keeps running the OLD binary:

    $ systemextensionsctl list
    *  -  …smsc95xx.driver (1.4/14)  SMSC95xxDriver  [activated enabled]
          …smsc95xx.driver (1.3/13)  SMSC95xxDriver  [terminating for upgrade via delegate]
    $ make -C dext status
      running: v13 …        <-- the kernel is still on the old one
      staged:  v14 …
      declared in tree: v14

The reported state is actively misleading, so `make status` compares running against staged against
declared. Safe sequence: unplug, bump CFBundleVersion in both Info.plists, make install, replug.

Whether holding a device open is strictly the cause is NOT established -- one upgrade did succeed
while the driver was present but failing Start(), and so holding nothing. Only the workaround is
established.
